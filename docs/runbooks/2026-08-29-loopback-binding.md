# Runbook: Loopback-only host binding for k3d-openchoreo cluster ports

Date: 2026-08-29 (fix implemented 2026-08-26, persistence proven 2026-08-29)
Status: VERIFIED - all 11 cluster ports bind 127.0.0.1 only, across a colima stop/start bounce.

## Problem

Every host listener that lima's ssh portForwarder created for the
`k3d-openchoreo` cluster bound `*` (all interfaces), making the k3s API
(6550) and the load-balanced service ports reachable from the LAN:

    ssh  ...  TCP *:6550  (LISTEN)   # k3s API
    ssh  ...  TCP *:8080  (LISTEN)
    ssh  ...  TCP *:8443 / *:10081 / *:10082 / *:11080 / *:11081 /
                *:11082 / *:11085 / *:19080 / *:19443 (LISTEN)

User mandate: everything configured on the local server, not an open IP.

## Root mechanism (the forwarding chain)

1. The k3d loadbalancer container `k3d-openchoreo-serverlb`
   (image `ghcr.io/k3d-io/k3d-proxy:5.8.3`, stateless nginx stream proxy)
   publishes its ports in the Colima VM. k3d creates it with wildcard
   guest bindings (HostIp "" / 0.0.0.0).
2. lima's guest agent detects guest listeners and the hostagent's ssh
   portForwarder (`colima.yaml: portForwarder: ssh`) creates a matching
   host listener per port via `ssh -O forward -L <hostIP>:<port>:<guestIP>:<port>`
   over the control master `~/.colima/_lima/colima/ssh.sock`.
3. The bind addresses are chosen by the `portForwards` rules in the
   generated `~/.colima/_lima/colima/lima.yaml` (regenerated by colima on
   every start). Stock rules:
   - `guestIPMustBeZero: true, guestIP: 0.0.0.0, hostIP: 0.0.0.0, 1-65535, tcp+udp`
     -> guest wildcard listeners become host `*` listeners (the exposure).
   - `guestIP: 127.0.0.1, hostIP: 127.0.0.1, 1-65535, tcp+udp`
     -> guest loopback listeners become host loopback listeners.

So the guest bind address fully determines the host bind address.
Verified empirically with throwaway nginx probes (2026-08-26):

    docker run -p 127.0.0.1:19999:80  -> host 127.0.0.1:19999 (LISTEN)
    docker run -p 19998:80            -> host *:19998 (LISTEN)   [pre-fix]

## The fix (two independent layers, defense in depth)

### Layer 1 (primary, fail-closed): serverlb publishes on guest loopback

Recreated `k3d-openchoreo-serverlb` on 2026-08-26 with identical config
except every port binding prefixed with `127.0.0.1`. server-0 was never
stopped, recreated, or restarted by hand (docker restart policy bounced
it during the colima bounce only; etcd state untouched).

Exact command used (DOCKER_HOST=unix:///Users/nnos/.colima/default/docker.sock):

    docker stop k3d-openchoreo-serverlb && docker rm k3d-openchoreo-serverlb
    docker run -d \
      --name k3d-openchoreo-serverlb \
      --restart unless-stopped \
      --init \
      --privileged \
      --userns host \
      --security-opt label=disable \
      --stop-signal SIGQUIT \
      --tmpfs /run --tmpfs /var/run \
      -e K3S_KUBECONFIG_OUTPUT=/output/kubeconfig.yaml \
      -v k3d-openchoreo-images:/k3d/images:z \
      --network k3d-openchoreo \
      -p 127.0.0.1:6550:6443 \
      -p 127.0.0.1:8080:8080 \
      -p 127.0.0.1:8443:8443 \
      -p 127.0.0.1:10081:10081 \
      -p 127.0.0.1:10082:10082 \
      -p 127.0.0.1:11080:11080 \
      -p 127.0.0.1:11081:5601 \
      -p 127.0.0.1:11082:9200 \
      -p 127.0.0.1:11085:11085 \
      -p 127.0.0.1:19080:19080 \
      -p 127.0.0.1:19443:19443 \
      --label app=k3d \
      --label k3d.cluster=openchoreo \
      --label k3d.cluster.imageVolume=k3d-openchoreo-images \
      --label k3d.cluster.network=k3d-openchoreo \
      --label k3d.cluster.network.external=false \
      --label k3d.cluster.network.id=fd3ff643f3e6de2b7fe9546c6d13a7086022ab3f14afe2859aba0a58c1e160ba \
      --label k3d.cluster.network.iprange=172.20.0.0/16 \
      --label k3d.cluster.token=<per-cluster random token; read the live value from `docker inspect k3d-openchoreo-serverlb` at apply time -- do not hardcode> \
      --label k3d.cluster.url=https://k3d-openchoreo-server-0:6443 \
      --label k3d.role=loadbalancer \

      --label k3d.version=v5.8.3 \
      ghcr.io/k3d-io/k3d-proxy:5.8.3

CRITICAL GOTCHA: the k3d-proxy entrypoint (`nginx-proxy`) reads its
upstream map from `/etc/confd/values.yaml` INSIDE the container's writable
layer. k3d writes that file at cluster-create time via docker exec; a
plain `docker run` of the image crash-loops with
`confd FATAL stat /etc/confd/values.yaml: no such file or directory`.
After recreating the container you MUST restore the file and restart:

    docker cp /tmp/lb-values.yaml k3d-openchoreo-serverlb:/etc/confd/values.yaml
    docker restart k3d-openchoreo-serverlb

### Layer 2 (belt and braces): lima override pins wildcard forwards to loopback

`~/.colima/_lima/_config/override.yaml` (lima user config, merged AFTER
the colima-generated lima.yaml; colima never touches it, so it survives
`colima stop/start` and even `colima delete` of the profile is not
required for it to persist):

    portForwards:
      - guestIPMustBeZero: true
        guestIP: 0.0.0.0
        guestPortRange: [1, 65535]
        hostIP: 127.0.0.1
        hostPortRange: [1, 65535]
        proto: tcp
      - guestIPMustBeZero: true
        guestIP: 0.0.0.0
        guestPortRange: [1, 65535]
        hostIP: 127.0.0.1
        hostPortRange: [1, 65535]
        proto: udp

This replaces the stock wildcard rules so that ANY guest wildcard
publish (present or future) is forwarded to host 127.0.0.1 only.
Caveat observed: a RUNNING hostagent does not pick this file up; it
takes effect on hostagent (colima) restart. Verified effective on the
fresh hostagent after the 2026-08-29 bounce: a wildcard probe
(`docker run -p 19998:80 nginx:alpine`) produced host listener
`127.0.0.1:19998`, and `nc -z <LAN-IP> 19998` was refused.

Why both layers: layer 1 fails closed even if lima config is reset
(loopback guest listeners only ever map to host loopback under the stock
rules); layer 2 covers any other container that ever publishes wildcard
in the guest, and protects against an accidental serverlb recreation by
k3d with wildcard binds.

## Side effects / operational notes

- `kubectl port-forward` processes do not survive a serverlb swap or a
  colima bounce (they die when the API connection at 127.0.0.1:6550
  drops; `kubectl proxy` reconnects in-process). After any bounce,
  re-establish them. `scripts/start-backstage.sh` has idempotent
  `ensure_*` functions for gitea 3333/3002, opencost 29003, signoz 3301,
  openchoreo-api 9090 and kubectl proxy 8001, but the script also starts
  Backstage itself; to avoid a duplicate Backstage, the forwards were
  restarted with the same nohup commands directly (pid files under
  ~/.rational-reserve/*-portforward-*.pid). The postgres forward
  (30432, svc/postgres-postgresql, ns backstage) is NOT covered by
  start-backstage.sh - restart it manually:

      nohup kubectl --context k3d-openchoreo -n backstage port-forward \
        svc/postgres-postgresql 30432:5432 > /tmp/postgres-portforward-30432.log 2>&1 &

- If `k3d cluster create` (or `k3d cluster delete` + create) is ever
  used to rebuild this cluster, k3d will generate the serverlb with
  wildcard guest bindings again. Layer 2 still pins the host side to
  loopback, but re-apply the Layer 1 procedure above and re-verify with
  the inverse proof.

    export DOCKER_HOST=unix:///Users/nnos/.colima/default/docker.sock
    docker inspect k3d-openchoreo-serverlb --format '{{json .HostConfig.PortBindings}}'
    lsof -nP -iTCP -sTCP:LISTEN | grep -E ':(6550|8080|8443|10081|10082|11080|11081|11082|11085|19080|19443) '
    LAN_IP=$(ipconfig getifaddr en0)
    for p in 6550 8080 8443 10081 10082 11080 11081 11082 11085 19080 19443; do
      nc -z -w2 "$LAN_IP" "$p" && echo "LAN:$p EXPOSED"; done   # expect silence
    kubectl --context k3d-openchoreo get nodes

## Rollback

There is no legitimate reason to re-expose the ports. If a specific
workflow genuinely needs LAN access to a port, forward that single port
on demand instead of reverting the binding, e.g.:

    ssh -N -L 0.0.0.0:8080:127.0.0.1:8080 localhost   # explicit, time-boxed

To fully undo (NOT recommended): recreate serverlb with the same
`docker run` as above but without the `127.0.0.1:` prefixes, restore
values.yaml identically, and remove the two portForwards rules from
`~/.colima/_lima/_config/override.yaml`, then `colima stop && colima start`.
