# Requirements Specification: M4 Networking (Cilium + Envoy Gateway)

**Document ID:** M4-NETWORKING-REQ-001  
**Version:** 0.1  
**Date:** 2026-06-30  
**Predecessors:** 2026-06-30-M4-Cost-Visibility-Requirements.md

---

## 1. Purpose

This document defines the requirements for the M4 networking plane of the developer portal platform. Today the k3d-openchoreo cluster uses the default Flannel CNI and has no ingress controller. M4 adds a modern CNI/service mesh layer (Cilium) and an ingress gateway (Envoy Gateway) so that platform services such as Backstage, Gitea, SigNoz, and OpenCost can be exposed on predictable hostnames with TLS-ready routing.

---

## 2. Vision

Platform services are reachable through a single Envoy Gateway ingress on well-known hostnames:

- `backstage.local`
- `gitea.local`
- `signoz.local`
- `opencost.local`

Cilium provides eBPF-based networking, observability, and Layer 7 policy enforcement. The combination gives the local IDP a production-like networking foundation without relying on cloud load balancers.

---

## 3. Scope

### In Scope

- A repeatable OpenTofu module that deploys Envoy Gateway into the cluster.
- HTTPRoute resources that route hostnames to the Backstage, Gitea, SigNoz, and OpenCost services.
- Local DNS resolution instructions (`/etc/hosts` or local resolver) for the `.local` hostnames.
- A cluster rebuild path that creates a new k3d cluster without Flannel and installs Cilium as the CNI, with Envoy Gateway layered on top.
- Install/teardown scripts and a smoke test that verifies each hostname resolves and reaches the correct service.

### Out of Scope

- Real public DNS or certificates (the local `.local` zone and self-signed or no TLS is sufficient for this milestone).
- Full Cilium service mesh features such as mutual TLS, cluster mesh, or bandwidth manager.
- Replacing the live k3d-openchoreo cluster CNI in-place (too disruptive); Cilium is introduced through a documented rebuild path.

---

## 4. Functional Requirements

### 4.1 Envoy Gateway Ingress

- FR-NET-1: Envoy Gateway runs in a dedicated namespace (e.g., `envoy-gateway`).
- FR-NET-2: Envoy Gateway exposes an external IP or NodePort reachable from the host.
- FR-NET-3: HTTPRoute resources route the following hostnames:
  - `backstage.local` -> Backstage frontend service (port 3001 externally; cluster service `backstage` port 3000).
  - `gitea.local` -> Gitea `gitea-http` service (port 3000).
  - `signoz.local` -> SigNoz frontend service (port 3301 mapped from cluster service `signoz` port 8080).
  - `opencost.local` -> OpenCost service (port 29003 mapped from cluster service `opencost` port 9090).
- FR-NET-4: `/etc/hosts` entries are generated by a helper script so the `.local` names resolve to the Envoy Gateway endpoint.

### 4.2 Cilium CNI Foundation

- FR-NET-5: A documented `k3d cluster create` invocation creates a fresh cluster without Flannel.
- FR-NET-6: Cilium is installed via Helm with Hubble enabled for observability.
- FR-NET-7: Core platform planes (control, data, observability, workflow) remain healthy after the CNI swap.

### 4.3 Operational Hygiene

- FR-NET-8: The module is version-pinned, repeatable, and managed via OpenTofu.
- FR-NET-9: Install and teardown are script-driven.
- FR-NET-10: A smoke test verifies HTTP 200 responses on each hostname.

---

## 5. Non-Functional Requirements

- The networking stack must fit within the existing Colima resource envelope or declare clear requirements.
- It must not destabilize M2/M3/M4 services already running.
- All configuration follows the existing repo-driven, version-pinned, ASCII-only conventions.

---

## 6. Success Criteria

- `scripts/install-m4-networking.sh` deploys Envoy Gateway and HTTPRoutes.
- `scripts/smoke-m4-networking.sh` returns HTTP 200 for `backstage.local`, `gitea.local`, `signoz.local`, and `opencost.local`.
- A documented `scripts/rebuild-cluster-with-cilium.sh` creates a fresh k3d cluster with Cilium and restores M2/M3/M4 state.
- `scripts/smoke-all.sh` continues to pass after Envoy Gateway is installed.
